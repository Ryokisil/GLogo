## HandsPOSとの比較

双方ともMVVMとClean Architectureの考え方を取り入れ、具体実装や共有状態への依存も残っています。HandsPOSは業務処理と外部機器の連携、GLogoは編集状態と描画の整合性に設計の重心があります。

| 観点 | HandsPOS: 共有資料の範囲 | GLogo: 確認した実装 |
| --- | --- | --- |
| 中心データ | `Transaction`、`Payment` | `LogoProject`、`LogoElement`、`ImageElement`など |
| 主な難しさ | 決済・保存・送信・印字・機器連携の整合性 | 編集・履歴・プレビュー・キャッシュ・保存画像の整合性 |
| 画面状態 | 取引履歴ではState／Eventを明示 | `@Published`、Binding、Combine、View内のState |
| UseCase | 操作可否・取消手続きなどの業務判断 | 画像調整確定・画像加工・インポート・描画調整など |
| DI | Container・画面用Dependenciesと既存Singletonが混在 | 一部で初期化時注入。内部生成や共有staticも存在 |
| Model | 業務データ、残額計算、支払明細の変更など | データに加えて画像解決・描画呼び出し・キャッシュも担当 |
| 非同期制御 | Task、世代番号、HUD所有者、画面終了を管理する領域がある | プリセットの世代番号、描画の遅延実行、処理中フラグなど |
| 永続化 | Realm等と業務データの変換が一部存在 | ModelのCodableとJSONファイル保存 |
| 主なテスト | 業務判定、State／Event、非同期競合 | 画像処理、保存、履歴、キャッシュ、旧形式復元、応答性 |

HandsPOSの設計方式が全画面で統一されているとは確認していません。GLogoについても、ファイルの配置だけで依存方向が適切だとは判断しません。

### HandsPOSの良いところと課題

- `DetermineVoidProcedureUseCase`のように、業務判断を型付きの結果として返す分離は、UIを生成せずに条件を検証できる点が強みです。
- 画面用Dependenciesは、画面が必要とする外部機能とテストの差し替え箇所を明示します。
- Actor、結果の鮮度、HUDの所有者を別々に管理する考え方は、それぞれ異なる非同期問題に対応しています。
- 一方、既存の大きなManager、Singleton、MVCの残存は、状態変更元と依存関係を追いにくくします。
- State／Eventや抽象化の導入では定義・配線が増え、移行時に既存操作を取りこぼす可能性もあります。段階的な移行と操作対応の検証が必要です。

### GLogoの良いところと課題

- スライダー操作の開始値を保持し、確定時の差分を履歴にする設計は、連続編集をUndoの単位へまとめるのに適しています。
- 即時プレビューと高品質描画を使い分け、プリセットでは古い完了結果を世代番号で破棄しています。
- `ImageElementRenderer`を画面と保存の両経路で利用し、見た目の処理の重複を減らしています。両経路の解像度や描画範囲が同じという意味ではありません。
- 保存Coordinatorは選定・加工・書き込みを注入でき、異常系もテストできます。
- 一方、Modelのプロパティ参照が画像取得・フィルタ処理・キャッシュ更新を起こすため、処理量や副作用を呼び出し側から把握しにくい箇所があります。
- ViewModelには編集種別や非同期機能が集中し、参照型Modelの変更と画面通知を揃える必要があります。
- 新しい編集属性を追加するときは、編集値だけでなくUndo、Revert、メタデータ、描画キャッシュ、保存形式まで影響します。

### 方式をそのまま移植しないための区別

| 論点 | 判断 |
| --- | --- |
| State／Event | SwiftUIではアラートや遷移も状態で表現できます。HandsPOSの単発Event方式を全画面へ導入する必要はありません。 |
| Eventの意味 | HandsPOSの画面EventとGLogoの編集履歴Eventは別物です。前者は表示操作の通知、後者は編集内容の適用・取り消しです。 |
| イベントソーシング | GLogoで確認した中心機構は上限付きUndo／Redoスタックです。永続イベントログを唯一の正とする基盤としては評価していません。 |
| Modelの振る舞い | `Payment`の残額計算のようなデータ固有のルールは自然です。画像I/Oや描画基盤の調整まで持つこととは区別します。 |
| DI | 初期化時の依存注入だけでも改善できます。Containerの有無やProtocolの数を品質指標にしません。 |
| Singleton | 共有インスタンス自体を一律に禁止しません。可変状態、寿命、同期方法、利用側の差し替え境界を確認します。 |
| 非同期 | CPU負荷の高い画像処理をメインから外すことは必要です。`Task.detached`を一律に除去せず、渡す値と完了結果の適用条件を確認します。 |

## 合意した責務分離の方向

ユーザーの方針は、責務が集中したViewModelを、機能や責務に対応する複数のViewModelへ分けることです。分割する具体型・ファイル名・移行順は、この文書の候補をもとに実装時に確定します。

分割の目的は、変更理由、状態の所有者、テスト境界を明確にすることです。行数だけを減らすためのextension分割では、同じクラスの責務集中は解消しません。

| 移す責務 | 適切な移動先 |
| --- | --- |
| 機能ごとの表示状態、ユーザー操作の受付、進捗・エラー表示 | 機能別ViewModel |
| 操作可否の判断、編集の確定計画、履歴の適用、保存の手順 | UseCase／Coordinator |
| 画像取得、描画、キャッシュなどの技術処理 | 既存Service／Repository／Rendererなど |
| 編集パラメータ、識別子、スナップショット、データ固有の計算 | Model／値型 |
| コントロールの表示、Binding、レイアウト | View |

### 共通状態の所有ルール

1. プロジェクト、選択要素、確定した編集履歴は、編集セッション内で一つの正となる所有者を維持します。まずは既存の`EditorViewModel`を入口として段階移行します。
2. 機能別ViewModelは操作途中の値、処理中表示、エラーなどを保持します。編集対象IDと操作開始時の状態を明示し、選択変更時の扱いを定めます。
3. 確定変更は共通の編集適用口を通し、履歴、変更フラグ、キャッシュ、通知を一度ずつ更新します。現在あるプレビューの一時変更と区別します。
4. 子ViewModel同士を相互参照させません。必要な状態・操作を狭い境界で渡し、親の全機能をそのまま公開しない方針とします。
5. 状態所有者を移す際は、親と子の双方に同じ可変状態を残さないようにします。子の変更通知を必要なViewへ届ける配線も確認します。
6. ViewModelの分割時に、Task、購読、スケジューラの寿命と終了条件を一緒に移します。画面の再評価でインスタンスや処理を再生成しないようにします。

## 検証する設計仮説

| 仮説 | 確認した根拠 | 実装前後の検証 |
| --- | --- | --- |
| 変更理由の違う処理が同居し、影響範囲が広くなっている | 二つのViewModelにテキスト・図形・画像・保存・AIなどの状態と操作がある | 機能別に読み書きする状態と呼び出し元を追跡し、一機能の変更で無関係な状態を触らないことを確認 |
| 可変参照と手動通知が、状態所有や反映順序の把握を難しくしている | `LogoProject`と要素は参照型。Undoなどで選択再設定や`objectWillChange.send()`を行う | 選択変更、Undo／Redo、非同期完了、View再生成をまたぐテストで表示とModelの一致を確認 |
| 内部生成と共有依存が、機能間競合の決定的なテストを難しくしている | ViewModel内の具体生成、`ImageElement`の共有static依存、保存時の生きたModel参照 | 初期化時注入と完了順を制御する代替実装を用意し、保存中のAI完了等を検証 |

## 段階的な進め方

| 段階 | 対象 | 完了条件 |
| --- | --- | --- |
| 0 | 状態所有と既存契約の整理 | 変更入口、選択、履歴、保存対象、Task寿命を説明でき、対象の既存テストを特定できる |
| 1 | 保存とAI・描画の同時更新境界 | 保存対象の固定方法と結果反映条件を決め、同時操作のテストを追加できる。詳細は保存文書を参照 |
| 2 | ViewModelの機能別分離とDI | 独立した一機能ずつ分離し、状態所有とテスト境界を移す。テキスト等の比較的閉じた機能から着手する候補がある |
| 3 | `ImageElement`の技術依存と履歴周辺 | Modelの取得・描画・キャッシュ責務を段階的に外し、保存・Undo・Revert・旧形式復元の契約を維持 |

段階1と2の具体的な着手順は、対象機能の競合調査で決めます。すべてを一度に分割したり、ViewModel分割と保存形式変更を同時に行ったりしません。

## テストと検証の扱い

- 既存テストの強みは、保存異常系、古いプリセット描画の破棄、Undo時のキャッシュ無効化、Codableの旧形式復元、メインキュー応答性です。
- 追加候補は、保存中のAI完了、要素変更・削除・Undo後の非同期完了、ViewModel分割後の通知と寿命、同一プロジェクトの保存順序です。全候補のテストが存在しないと断定したものではありません。
- 詳細文書の「既存テスト」は所在と検証内容の記録であり、今回の実行成功を示しません。
- 調査記録の作成では文書を追加・更新しました。その後、Xcodeで閲覧できるよう`docs`のフォルダ参照を追加しています。アプリ実装と永続化形式は変更していません。
- 実装時は対象のテストを実行し、変更範囲に応じてビルド、`swiftformat GLogo/ --lint`、UI・保存結果の検証を行います。保存・描画・履歴の変更では回帰テストの意味も再確認します。
